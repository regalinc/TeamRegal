# Housecall Pro Technician Dashboard

Pulls jobs and technicians from the [Housecall Pro Public API](https://docs.housecallpro.com/) hourly via GitHub Actions, and shows a live per-technician job dashboard as a static site on GitHub Pages.

## How it works

- `scripts/sync.js` — calls `GET /employees`, `GET /jobs`, and `GET /estimates`, groups jobs by assigned technician, and writes the result to `docs/data/*.json`. Includes each job's tags and `total_amount`/`outstanding_balance` (Housecall Pro reports these in cents; the dashboard converts to dollars). The synced `lead_source` comes from the **customer** record embedded in each job response (`job.customer.lead_source`), not the job's own `lead_source` field — Housecall Pro treats lead source as an attribute of the customer (set once, however they originally found the company), and the job-level field is typically unset. Canceled jobs (`user canceled`/`pro canceled`) are kept in the synced data — the Company Metrics page needs them to compute a cancellation rate — but `computeStats`/`computeScorecardStats` in `shared.js` exclude them from every other metric, so nothing else changes.
- `.github/workflows/sync.yml` — runs the sync script hourly (and on manual trigger), then commits any changed data files. The data file is several MB (more as the year goes on — see "Adjusting the data window" below), so consecutive bot-only syncs **amend and force-push over the previous data commit** rather than stacking a new commit each time — otherwise a frequent cadence would bloat the repo's git history within days. A real (human) commit always breaks the chain and gets a fresh data commit stacked after it, never amended. This means the data-commit history isn't preserved — only the latest sync is ever visible in `git log`, by design. Note: GitHub Actions' `schedule` trigger is best-effort and gets deprioritized under load — the cron runs at `:17` past the hour rather than `:00` specifically because `:00`/`:30` are documented as the most congested minutes (everyone else's cron fires there too); on `0 * * * *` actual runs were observed landing 2.5-11 hours apart despite the hourly setting. Moving off the hour mark should land much closer to hourly, but there's still no hard guarantee — check the Actions tab for actual run times if the dashboard's "Last synced" looks stale, and trigger manually if you need it fresher right away.
- `docs/` — static dashboard (plain HTML/CSS/JS, no build step) served by GitHub Pages. `index.html`/`app.js` and `admin.html`/`admin.js` share `shared.js` (data formatting, scorecard rendering, period math); `tv.html`/`tv.js` reuses `shared.js`'s data/compute helpers but has its own rendering and its own stylesheet (`tv.css`) since the TV layout has nothing in common visually with the other two. Three pages total:
  - `index.html` / `app.js` — the **technician view**. A **Team summary** row (raw Total jobs/Total revenue/Average ticket/Completion rate) at the top, then a **scorecard per technician** with the underlying job list tucked behind a "N jobs in view" toggle rather than shown by default. Filter bar covers technician/job text search, a multi-select technician picker (with employee-tag quick-filter buttons), business unit, tag, status, and a reporting period.
  - `admin.html` / `admin.js` — the **department view** (linked from the technician view's header). Same scorecard layout, grouped by `business_unit` instead of by technician, with a company-wide summary row at top. See "Department (admin) view" below.
  - `tv.html` / `tv.js` / `tv.css` — the **TV kiosk view**, one department's leaderboard per unattended shop-floor screen. See "TV kiosk view" below.

  Both pages poll `data/dashboard.json` every 60 seconds in the browser. **Scorecards on both pages use tag-based numbers, not raw job counts** — see `computeScorecardStats` in `shared.js`: "Jobs" only counts jobs tagged `Opportunity`, "Leads"/"Leads sold" use the `TGL`/`TGL Sold` tags, "RCC sold" uses `Membership Sold` (Housecall Pro's own membership-sales report isn't exposed via the public API), "$0 Call" (displayed name; the underlying tag, `stats.ifo`, and every `kpiTier`/`kpiClass` metric key stay `IFO`/`"ifo"` since those have to match Housecall Pro's real tag) and "Accessory sold" use their own like-named tags. The page-level summary rows are the one place raw totals (`computeStats`) still show, by design — that's the "how much actually happened" number, scorecards are "how the business tracks it."

  **Every total — Jobs, Revenue, Avg ticket, Leads, Leads sold, RCC sold, $0 Call, Accessory sold — only counts completed jobs.** `scheduled`/`needs scheduling`/`in progress` jobs are excluded from all of them, in both `computeStats` (team/company summary) and `computeScorecardStats` (every scorecard and the TV kiosk, since it reuses the same function). This isn't just a job-count nicety — a `scheduled` or `in progress` job's `total_amount` is frequently a pre-set quote for a visit that hasn't happened yet, not real revenue, and every one of the tag-based metrics represents an outcome decided *during* that visit (IFO, Accessory sold, a lead converting), which isn't knowable before the visit happens either. Confirmed as a real bug, not just a theoretical one — on the first day of a new month, with most of the month's work still ahead, a technician's Revenue for a business unit was showing thousands of dollars from scheduled/in-progress jobs alone, days before any of that work had actually happened. **Completion rate is the one exception, unaffected by this** — it's deliberately a ratio of `in progress + complete` (started) vs. complete, not a "total," and still needs in-progress jobs in its denominator to mean anything (otherwise a department mid-way through a pile of unfinished work would misleadingly read as 100% complete). `NOT_YET_STARTED_STATUSES`/`COMPLETE_STATUSES` in `shared.js` are the two status sets this all keys off of.

  **Revenue on the technician view is split, not full-credit.** Housecall Pro splits a job's revenue evenly across however many technicians were on site for it (a $100 job splits $50/$50 for two, $33.33 each for three, ...), rather than crediting every assigned technician the full amount — so `computeScorecardStats` divides each job's `total_amount` by its `assigned_employee_ids.length` when called with `{ splitRevenue: true }`, which only the technician view (`app.js`) passes; the tile is labeled **"Revenue (split)"** there to make that explicit. Department cards (`admin.html`) and the page-level raw totals keep summing full job amounts — a job belongs to one department regardless of how many people worked it, so splitting doesn't apply at that level, and "Total revenue" at the top is still meant to read as "how much actually happened," not an attribution. There's no split/commission field anywhere in Housecall Pro's public API (checked the full resource list — Jobs, Job Invoices, `InvoiceItem`, Estimates, Employees, everything), so this is computed from `assigned_employee_ids`, which is already synced; no sync.js change was needed.

  **Avg ticket on the technician view is deliberately split too, by extension — Jobs (the denominator) isn't.** `avgTicket = totalRevenue / totalJobs`, and only `totalRevenue` picks up the split; `totalJobs` (the `Opportunity`-tag count) is still a raw count, one per job regardless of headcount. So Avg ticket answers "how much revenue am I personally credited with, per job I'm credited with" — not "how big are the jobs I work." Two technicians on the same $100 two-person job both show that job in their Jobs count, but each shows $50 toward their own Revenue and thus a lower Avg ticket than if they'd worked it solo. Confirmed intentional, not a bug — asked and kept this way explicitly rather than switching Avg ticket to unsplit job totals.

  **Revenue accepted on estimator cards is deliberately *not* split, unlike job Revenue.** Estimates can also have more than one `assigned_employee_ids` entry (110 in the synced data as of writing, 44 of them currently approved) with the exact same full-credit-per-assignee shape as jobs — but this was explicitly asked about and left as full credit rather than divided by assignee count. If that decision changes later, the fix mirrors the job Revenue one: divide `approved_amount` by `assigned_employee_ids.length` in `computeEstimatorStats` (`app.js`).

  **Apprentices don't get their own card, and don't count toward a job's revenue split.** `APPRENTICE_TECH_IDS` in `shared.js` is a manual id list (no dedicated Housecall Pro tag exists for this yet — same pattern as `MANUAL_AVATAR_OVERRIDES` above) of technicians who are training alongside a real tech rather than working independently yet. Two effects follow: `jobRevenueCents` excludes their id when counting a job's split — a job with one real tech and one apprentice splits as a 1-person job (the real tech gets full credit), not 50/50 — and they never appear as their own scorecard or TV row (`getRosterTechs` in `app.js`, `departmentOf` in `tv.js`) or as a selectable option in the technician picker/quick-filter buttons, even via a hand-crafted `?techs=` URL. This is scoped to individual attribution only — department cards (`admin.html`) and the page-level company totals still count their jobs normally, same as anyone else's, since those aren't split by headcount in the first place. Remove an entry from `APPRENTICE_TECH_IDS` once that person is working independently.

  The **technician view** also has three estimate-based tiles per scorecard (`app.js`), computed from the synced `estimates` — see "Estimates" below.

  **HVAC Installation techs don't get individual scorecards at all — one team card covers the whole roster instead.** They don't control their own job pipeline (work is sold and handed to them, not generated by their own sales/upsell activity), so an individual's Revenue/Jobs/Avg ticket mostly reflects what landed on their schedule, not their own performance — there isn't a meaningful individual number to show. `INSTALLATION_TEAM_TECH_IDS` in `app.js` is a manual id list (same pattern as `APPRENTICE_TECH_IDS`/`MANUAL_AVATAR_OVERRIDES` in `shared.js`) — the complete HVAC Installation roster as of writing, so a new hire in that department needs adding there too. Unlike apprentices, these are real techs and stay fully selectable in the technician picker/quick-filters; the roster loop just skips rendering an individual card for them (`render` in `app.js`).

  **The team card (`renderInstallationTeamCard`, `app.js`)** appears once, ahead of the individual cards, whenever the current roster includes any HVAC Installation tech — always aggregating the full 9-person roster regardless of whether the filter narrowed to a specific subset of them (e.g. `?techs=Jack%20Tomlinson` still shows the whole team's number, not a Jack-only slice, since there's no valid individual number to fall back to). It's scoped to their **BU 10 work only** — `businessUnitCode(job.business_unit) === "10"` — deliberately excluding jobs they picked up in another business unit while helping out another department when Installation's own queue was light; that occasional cross-department work isn't really "their" job. Revenue is unsplit (full job amounts, not divided by assignee count) since this is a team total, not a personal attribution, same convention `admin.html`'s department cards use. Jobs is a raw count (`rawJobCount` on `computeScorecardStats`, `shared.js`) rather than tag-filtered — confirmed against synced data that HVAC Installation jobs aren't reliably tagged `Opportunity` (one tech's entire year of completed jobs had zero tagged `Opportunity`), same convention business unit 50 (Plumbing AOR) already uses company-wide via `RAW_JOB_COUNT_BU_CODES`. Leads, Leads sold, RCC sold, $0 Call, and the three estimate tiles are hidden (`hiddenTiles` on `renderScorecard`) since that department doesn't work off those tags and doesn't write estimates. None of this touches `admin.html`'s BU 10 department card, which keeps its own separate job-level rule (jobs tagged `Oncall Air`) and still shows all nine base tiles — a business unit's job-level convention and which techs get folded into the team card (an employee tag) are different concepts that happen to both loosely get called "BU 10" in conversation.

  **KPI coloring (green/amber/red) isn't just a TV kiosk thing — Avg ticket/IFO/Leads/Accessory sold tiles color the same way on `admin.html`'s department cards and on `index.html`'s technician cards**, using the exact same targets: `KPI_THRESHOLDS_BY_BU`/`tier`/`kpiTier` now live in `shared.js` (not duplicated per page — see "KPI tiles are colored..." under TV kiosk view below for the tiers and BU-by-BU numbers) and `renderScorecard`/`renderMiniStat` accept an optional `kpiBuCode` to grade against. Department cards on `admin.html` pass it unconditionally (`renderDeptCard` in `admin.js`) since a card is already scoped to one business unit. Technician cards on `index.html` only pass it when the **business unit filter** is narrowed to a single BU (`app.js`) — an unfiltered tech's jobs can span two BUs with different goals (e.g. an HVAC Service tech works both BU 30 and BU 40), so there's no one goal to grade an unfiltered card against; picking a BU in the filter scopes the tech's own jobs to just that BU too, so the number being graded and the goal it's graded against finally match. `kpiTier` returns null (neutral, no color) for any BU with no targets defined (Office, installation, BU 10/50) or any metric a BU doesn't have a target for yet (e.g. Leads on BU 70/80) — same graceful fallback as the TV. **The company-wide summary row at the top of `admin.html` stays uncolored and unchanged** — it blends every department into one number, and there's no single BU's goal that applies to a blended total, so coloring it would be misleading rather than useful.

**Period filter:** Today / This week / Last week / This month / Last month / Year to date scope the team summary *and* every technician's scorecard consistently — pick "This month" and both the top numbers and each person's tiles reflect only that month's jobs. Period boundaries are computed from each job's `schedule.scheduled_start` (there's no separate completion/invoice date synced yet), in the viewer's local time, with weeks starting Sunday. Only options the synced window can answer accurately are offered — see below. **Both pages default to "This month" on a fresh load** (no `?period=` in the URL) — pass `?period=` (empty) or another value explicitly to override, e.g. for a bookmarked screen that should show all synced time.

**Business unit vs. technician tags:** the "Business unit" filter uses Housecall Pro's native `job_fields.business_unit` field on each job (set under Settings → Business Units in Housecall Pro). Technicians also carry their own employee tags (shown as small chips on each card) — useful for role/specialty context, but those aren't currently a filter; business unit is the source of truth for department-style reporting since it's a structured field rather than free-text tags.

**Privacy note:** the dashboard data intentionally excludes customer phone/email and full street address (only city/state/zip), and technician contact info, since this repo is public. Revenue figures (total_amount, outstanding_balance) *are* included, by request — if that's no longer wanted, remove those fields in `toPublicJob` in `scripts/sync.js`. If you make the repo private (requires a paid GitHub plan for Pages), you can widen `toPublicJob`/`toPublicTechnician` to include more fields, like full addresses or contact info.

## One-time setup

1. **Create the API key** in Housecall Pro (requires the MAX plan): account settings → API keys. Copy it.
2. **Push this project** to your GitHub repo:
   ```
   git init
   git add .
   git commit -m "Initial Housecall Pro dashboard"
   git branch -M main
   git remote add origin <YOUR_REPO_URL>
   git push -u origin main
   ```
3. **Add the API key as a repo secret**: repo → Settings → Secrets and variables → Actions → New repository secret → name `HCP_API_KEY`, value = your key.
4. **Enable GitHub Pages**: repo → Settings → Pages → Source: "Deploy from a branch" → Branch: `main`, folder `/docs`.
5. **Run the sync once manually**: repo → Actions → "Sync Housecall Pro data" → Run workflow. This populates `docs/data/` for the first time.
6. Visit the Pages URL (shown in Settings → Pages once it's live, usually `https://<you>.github.io/<repo>/`).

After that, the workflow refreshes data hourly on its own — no machine or Claude session needs to be running.

## Local testing

```
$env:HCP_API_KEY="your_key_here"   # PowerShell
node scripts/sync.js
```

Then serve `docs/` with any static file server and open it in a browser — opening `index.html` directly via `file://` won't work because the dashboard fetches `data/dashboard.json` over HTTP. If you don't have Node/Python handy, `_serve.ps1` in this repo is a zero-dependency PowerShell static server:

```
powershell -ExecutionPolicy Bypass -File _serve.ps1
```

Then visit http://localhost:8743/index.html.

## Bookmarkable views (e.g. for an external screen/TV)

The dashboard reads its filter state from the URL on load, so a single link can be a fixed view for a lobby or shop-floor screen:

| Param | Effect | Example |
|---|---|---|
| `techs` | Show only these technicians (comma-separated names or ids; case-insensitive) | `?techs=Jack Tomlinson,Trevor McWilliams` |
| `bu` | Pre-select a business unit | `?bu=40 HVAC MAINT` |
| `tag` | Pre-select a job tag | `?tag=Opportunity` |
| `status` | Pre-select a status | `?status=in progress` |
| `period` | Pre-select a reporting period | `?period=month` (values: `today`, `week`, `lastweek`, `month`, `lastmonth`, `ytd`) |
| `q` | Pre-fill the text search | `?q=furnace` |

Params combine (e.g. `?techs=...&bu=...`). Spaces need URL-encoding (`%20` or `+`) if you're typing the link by hand — most browsers do this automatically when you paste a link with spaces into the address bar. When `techs` is set, the unassigned-jobs section and per-technician stats scope to just that roster; the viewer can still use the filter bar on top of it. For a fully unattended screen with no filter bar at all, see "TV kiosk view" below — a separate page built for that specifically, rather than a mode bolted onto the interactive one.

**Picking technicians from the UI:** the "All technicians" control in the filter bar is a searchable multi-select checklist (sorted alphabetically) — no need to hand-build a `techs=` URL. Selecting/deselecting technicians there updates the address bar's `techs` param live, so once you've picked the set you want, the current URL is already the bookmarkable link for that view.

## Department (admin) view

`admin.html` groups the same synced jobs by `job_fields.business_unit` instead of by technician, so management can see department-level totals (HVAC Service, Plumbing Installation, etc.) without individual technician names. It shares the filter bar (search/tag/status/period) and scorecard styling with the technician view, minus the business-unit filter itself (redundant — that's now the grouping) and the technician picker. Jobs with no business unit set land in a trailing "No business unit set" card rather than being dropped.

Each department has a **fixed color identity** (a top border + dot on its card) assigned by business-unit code, not by rank or filter state, so a department's color never changes as you filter — see `DEPT_COLOR_VARS` in `admin.js` and the `--series-*` custom properties in `style.css` (theme-aware, validated CVD-safe order). Every department renders as a full-width card in a vertical stack (not a multi-column grid) so each one gets the same prominent treatment.

**Cancelled calls** shows at two levels: a company-wide tile in the summary row (count + rate across the current filtered/period view), and a "Cancelled" mini-stat on every individual department card scoped to just that department's jobs. Both use `computeCancellationStats` in `shared.js` — the one place canceled jobs are counted rather than excluded from a stat.

**Lead source performance** groups jobs by the **customer's** `lead_source` (see `scripts/sync.js` above — distinct from business unit/technician) — **every job from that source counts, tagged or not**; a job also tagged for another tracked program (`Opportunity`, `TGL`, `IFO`, `Membership Sold`, `Accessory Sold`, ...) still originated from this lead source and belongs in its total. Sources with $0 revenue in view are dropped entirely — not useful to show — and jobs with no lead source land in an "Unknown source" bucket (muted gray, not a real category, same treatment as "No business unit set"). Ranked by revenue, the top 6 render as a **column chart** (`renderLeadSourceChart` in `admin.js`) with bar height proportional to revenue (a 6% minimum height keeps a small source visible as a color swatch rather than invisible) — lead source revenue is typically heavily skewed (one channel can outweigh another 1000:1), so equal-width/equal-height segments would misrepresent the relative sizes; a genuinely small source now reads as small. Each bar's name/count/$ label sits below it (never inside), in its own fixed-height zone independent of the bar, so a long wrapped label can never compress or distort the bar's height. Sources past the top 6 sit behind a "+N more lead sources" toggle, shown as a smaller multi-column card grid. Both cancellation-per-department and lead source performance are **Company Metrics (`admin.html`) only** — the technician view doesn't show them.

**This is not real access control.** The whole site is public with no login (same as the technician view), so `admin.html` is just a different, unadvertised-beyond-the-nav-link page — anyone with the URL can view it. If you actually need to restrict who can see it, the realistic path on this architecture is making the GitHub repo private and upgrading to a paid GitHub plan (Pro/Team/Enterprise) — GitHub Pages on a private repo then requires being a logged-in collaborator, which is real auth tied to GitHub identity rather than obscurity. Ask if you want that set up.

## TV kiosk view

`tv.html` / `tv.js` / `tv.css` are a third, separate page — not a mode of the interactive dashboard — built for an unattended shop-floor TV. No filter bar, no nav, nothing clickable; it just shows one screen's leaderboard and refreshes itself. Not linked from the other pages (there's no reason a desk-side viewer would navigate to it); each physical TV is just pointed at its own URL.

**Required:** `?dept=` — one of `Plumbing Installation`, `HVAC Installation`, `Office`, `30`, `40`, `70`, `80` (matching is forgiving on spaces/hyphens/underscores/capitalization — see below). Anything else shows an on-screen error listing the valid values instead of a blank page. Example: `tv.html?dept=30`.

**Seven screens, not five.** Three (`Plumbing Installation`, `HVAC Installation`, `Office`) show one tag-based department's full roster — except `HVAC Installation`, which is a single team screen rather than a ranked roster (see below). The other four (`30`, `40`, `70`, `80`) are business units, not tags: an "HVAC Service"-tagged tech's jobs actually land under either BU 30 (service) or BU 40 (maintenance) in Housecall Pro, and a "Plumbing Service"-tagged tech's under BU 70 or 80, so each business unit gets its own dedicated screen rather than blending both into one "HVAC Service"/"Plumbing Service" leaderboard — that blended version existed briefly but put 7 techs × 2 business units × 8 metrics on one screen, which was too dense to read. `?dept=HVAC%20Service`/`?dept=Plumbing%20Service` are no longer valid for this reason; a TV that needs to show BU-30 work is pointed at `?dept=30` directly.

**`HVAC Installation` is a team screen, not a ranked roster.** Installation techs don't control their own job pipeline — work is sold and handed to them — so there's no meaningful individual number to rank them on (same reasoning as the technician view's `renderInstallationTeamCard` in `app.js`; the roster/tile exception list, `INSTALLATION_TEAM_TECH_IDS`, and hidden-tile set, `INSTALLATION_TEAM_HIDDEN_TILES`, both live in `shared.js` so the two pages share one definition). Instead of the featured-card-plus-list layout every other screen uses, `renderInstallationTeamScreen` (`tv.js`) fills `.tv-main` with one large centered block (`.tv-team` in `tv.css`): a monthly revenue goal tracker on top, then 5 large team-wide tiles (Revenue, Avg ticket, Jobs, Completion, Accessory sold — `installationTiles`) below, both scoped to the team's BU 10 work only. The goal tracker (`renderInstallationGoal`) always compares the **current calendar month's** revenue against a target from `INSTALLATION_MONTHLY_GOALS` in `tv.js` — a plain object keyed `"YYYY-MM"` (e.g. `{"2026-08": 475000}`) that needs a new entry added by hand each month; a month with no entry renders "No revenue goal set for [Month] yet." instead of a broken or zeroed bar. This goal figure is deliberately independent of the screen's own `?period=` — a manager setting `?period=week` to check recent pace shouldn't also shrink the monthly goal's numerator — while the 5 tiles below it do respect `?period=` like every other screen's metrics.

**Department mapping** (`departmentOf` in `tv.js`): the four field-tech tags (`Plumbing Service`, `Plumbing Installation`, `HVAC Service`, `HVAC Installation`) are real employee tags already used elsewhere (the technician-view quick-filter buttons) — a BU screen's roster (`BU_DEPTS` in `tv.js`) is whichever of these tags actually works that business unit (30/40 → "HVAC Service" techs, 70/80 → "Plumbing Service" techs). There's no equivalent "Office" tag, so `Office` is a catch-all — anyone not carrying one of the four field tags — rather than a hardcoded list of office-specific tags (`Customer Service Specialist`, `Estimator`, `Office Manager`, ...) that could go stale as new ones appear. `EXCLUDED_TECH_IDS` drops three accounts that showed up in that catch-all but aren't real people (Marketing Department, Urgency Plumbing, Urgency HVAC — dispatch/system accounts). One known consequence of the catch-all: a technician with no department tag at all lands on the Office TV regardless of their actual role (e.g. a field tech missing a tag) — a real gap in Housecall Pro's tagging, not a bug here, but worth knowing about if an Office TV shows someone unexpected.

**Optional params:** `?period=` (same values as the rest of the app — `today`/`week`/`lastweek`/`month`/`lastmonth`/`ytd`; defaults to `month`).

**Metrics:** every technician tile — the featured card or a list row — shows the same 8: Revenue, Avg ticket, Completion, Jobs, Leads, Leads sold, $0 Call (IFO), Accessory sold (`metricTiles` in `tv.js`, drawing on the same `computeScorecardStats` fields the desktop scorecards use).

**Ranking:** every technician in the roster is ranked by split Revenue (`computeScorecardStats(jobs, { splitRevenue: true })`, same metric as the technician view's "Revenue (split)") for the selected period, highest first — including $0 techs, ranked last, so the full roster is always visible rather than only whoever has activity. Every screen shows one large "featured" card for the current #1 (big photo, name, rank, the 8-tile grid), with everyone else as a smaller ranked row in a list beside it — #1 always holds the featured spot; there's no timer or rotation, it just re-sorts on every data refresh. On a BU screen (`30`/`40`/`70`/`80`), ranking is scoped to just that BU's jobs, so the same tech can rank very differently across their two screens (e.g. #1 in BU 30 revenue but #5 in BU 40) — `buildBuRanked` in `tv.js` vs. the unscoped `buildRanked` the three tag-only screens use.

A BU screen's header and featured-card rank subtitle both show the business unit's exact name as synced from Housecall Pro (e.g. "30 HVAC SERVICE"), read live off a matching job rather than hardcoded, so it always matches what `admin.html` shows for the same BU (`businessUnitLabelForCode` in `tv.js`).

**KPI tiles are colored per business unit, per Regal's own targets, three tiers deep** (`KPI_THRESHOLDS_BY_BU`/`tier`/`kpiTier` in `shared.js`, keyed by BU code — shared with `admin.html` and `index.html`, see above) — solid green (`.tv-good`), amber (`.tv-warn`), or red (`.tv-bad`) fill on the tile, not just the number, so it reads at a glance from across a room. On the TV, `kpiClass` in `tv.js` just maps a screen's `DEPT` straight into `kpiTier` — a tag-only screen (Office, installation) isn't a BU code, so `kpiTier` returns null and those tiles stay neutral automatically. Amber is a "close but not there" band off the goal (15% by default, but overridable per metric — see IFO below) rather than a hard green/red cutoff; `tier()` applies that buffer to every metric below, on whichever side of the goal is the bad direction for that metric (below goal for a floor like Avg ticket, above goal for a ceiling like IFO). Amber uses dark text on its fill, unlike green/red's light text — a light-on-amber pairing that matches the other two tiers reads poorly, so this one tile flips the contrast direction instead. Defined so far:
- **30** — IFO under 7.5% of jobs good / 7.5-10% amber (`stats.ifo / stats.totalJobs`, a wider band than the default 15% buffer would give — `buffer: 1/3` on this one metric), Avg ticket $450+ good / down to $382.50 amber, Leads (lead turnover) 1 per 12 jobs or better good / down to roughly 1 per 14 amber, Accessory sold 1 per 8 jobs or better good / down to roughly 1 per 9.4 amber
- **40** — same four metrics as 30, except Avg ticket's bar is $250+ good / down to $212.50 amber, instead of $450/$382.50
- **70** — IFO and Accessory sold same bars as 30/40, Avg ticket $500+ good / down to $425 amber, no Leads target yet (tile stays neutral)
- **80** — IFO and Accessory sold same bars as 30/40, Avg ticket $300+ good / down to $255 amber, no Leads target yet (tile stays neutral)

Each BU's thresholds are written out in full even where two BUs' rules happen to match today (IFO/Accessory sold are currently identical across 30/40/70/80) — editing one BU's target should never silently change another's. Revenue, Completion, Jobs, and Leads sold have no target yet and stay neutral everywhere. A tech/section with zero jobs in the period renders every ratio-based KPI neutral too, rather than a misleading pass or fail with no underlying data. Any BU not listed in `KPI_THRESHOLDS_BY_BU` stays fully neutral everywhere it appears (TV, department cards, filtered technician cards) — add a new entry (keyed by that BU's code) once targets exist for it.

**Forced dark mode, not theme-adaptive.** Unlike the rest of the site (`prefers-color-scheme`-based), `tv.css` hardcodes the dark palette unconditionally — smart TV browsers are inconsistent about reporting an OS-level light/dark preference, and this is a fixed always-on display rather than something a person toggles, so relying on auto-detection risked an unpredictable result per device.

**Sizing is viewport-relative (vw/vh/clamp), not fixed px — this matters and is easy to get wrong.** A browser renders CSS pixels at a fixed reference size regardless of physical screen size, so a layout sized in fixed px/rem (fine for a normal browser window) renders as a small block in the corner of a 1920x1080 or 4K TV rather than filling it — confirmed by testing at 1920x1080 before switching to viewport units, where the entire page rendered into roughly a 750x450px corner. `tv.css` uses `vw`/`vh` for layout dimensions and `clamp()` for font sizes so the page fills whatever screen it's opened on and scales proportionally across resolutions, rather than needing a different build per TV size.

**An unattended TV won't necessarily pick up a code change just because someone walks up and hits refresh, so it fixes itself instead.** GitHub Pages serves `tv.html`/`tv.css`/`shared.js`/`tv.js` with `Cache-Control: max-age=600` each — a browser that's within that 10-minute window can serve the old cached copy straight from disk with no network request at all, refresh or not. Two things fix this: `tv.html`'s `<script>`/`<link>` tags carry a manually-bumped `?v=` query string (`ASSET_VERSION`, see the comment in `tv.html`) — a bumped version is a genuinely different URL, so it's a cache **miss** regardless of how fresh the old entry still looks, not just a freshness check that a mid-window browser could still pass. Bump it any time `tv.css`/`shared.js`/`tv.js` changes. That alone isn't enough on its own, though — the versioned tag only helps once `tv.html` itself gets re-fetched, and the 60-second `loadData` poll (`tv.js`) only ever re-requests `data/dashboard.json`, never the HTML/JS/CSS themselves. So `tv.js` also reloads the whole page on its own every `RELOAD_INTERVAL_MS` (6 hours) — there's no user input state on this page to lose, so a reload is always safe, and this means a TV left running for weeks picks up a shipped change within hours on its own, without anyone needing to visit it in person or know to hard-refresh.

**A list row's tile sizing also scales with how many rows are on screen, not just viewport size.** Flexbox already shrinks each `.tv-row` to fit however many people are in the roster (5 on Plumbing Service screens, 6 on HVAC Service, and it'll keep changing as staff come and go) — but the metric tiles *inside* a row used to be sized off a flat vh percentage that assumed a specific row count, so a screen with more rows than that got shorter rows without the tile content shrinking to match, and the two stacked rows of tiles inside each row overflowed into each other. `renderRoster` (`tv.js`) sets a `--row-count` custom property on `.tv-list`, and every vh-based size in `.tv-row`/`.tv-row-tile` that contributes to a row's vertical footprint (`tv.css`) is expressed as `(5-row value * 5 / var(--row-count))` — anchored to 5 because that was the confirmed-working case, so a 5-row screen renders identically and anything with more rows gets a real, proportional reduction instead of none.

**Every photo — featured or row-sized — requests the high-res `original`, not just the featured one.** Housecall Pro's API only ever returns a 40x40 thumbnail URL, but an `original` (1000px+) sits at the same path under a sibling folder (`largeAvatarUrl` in `shared.js`); a caller that needs a bigger photo swaps to it and falls back to the thumb (then to colored initials) if that employee doesn't have one stored. It's tempting to assume only the big featured photo needs this — the desktop dashboard's ~36px avatars are fixed px and already native resolution with the thumb — but the TV kiosk's "small" row photos are sized in vw/vh like everything else on the page (see above), so they scale well past 40px on a real screen too and looked upscaled/blurry before both `renderFeatured` and `renderRow` in `tv.js` requested the `original`. Not every employee has one stored (older/re-synced accounts may only have the thumb) — that shows as a soft photo even after this fix, and the real fix is having that person re-upload their photo in Housecall Pro; nothing here can conjure resolution that was never uploaded.

**A few employees have a standing manual override instead, because a re-upload didn't fix it.** Six technicians re-uploaded their photo in Housecall Pro and still had no resolvable `original` hours later (confirmed by directly probing the CDN, not a fluke) — for whatever reason, their upload path just doesn't generate one. `MANUAL_AVATAR_OVERRIDES` in `shared.js` maps their technician id straight to a locally-hosted file under `docs/assets/tech-photos/` (resized to 800x1200 from the original 12-47MB studio files before committing — full studio resolution is wildly more than a TV needs and would bloat the repo), and `largeAvatarUrl` checks that map before ever trying Housecall Pro's CDN for those ids. Keyed by id, not name, so a name change can't cause a mismatch. This is a standing workaround, not a permanent fix — if Housecall Pro's own `original` ever becomes available for one of these people, remove their entry; nothing here checks for that automatically.

## Estimates

The technician view's scorecards (`app.js`) carry three tiles pulled from `GET /estimates` rather than jobs:

- **Estimates given** — count of estimates created within the selected period, assigned to that technician (`estimate.created_at`, same field Housecall Pro's own reporting uses). **One narrow exception:** Andrew (Andy) Rouscher's card scopes by the estimate's scheduled site-visit date instead (`estimate.schedule.scheduled_start`) — his created_at-based count didn't match his actual calendar for the same date range (30 vs. 19; landed at 20 after the switch), so `SCHEDULE_SCOPED_ESTIMATOR_IDS`/`estimateGivenDate` in `app.js` swap the date field just for his id. Every other estimator still uses `created_at`; this isn't a change to the metric's default definition. Two things drop out of his count entirely (not just shift to a different period) rather than falling back to `created_at`: an estimate with no scheduled visit at all (phone/remote estimates don't have one), and — since "This month" runs through the end of the month, not capped at today — a visit scheduled for later that hasn't happened yet, so an unpresented estimate doesn't drag down his Closing % before he's even had the chance to close it. It starts counting once its scheduled date actually passes. `schedule` had to be added to what `toPublicEstimate` (`scripts/sync.js`) syncs for estimates — it wasn't captured before this.
- **Estimates approved** — of those same period-given estimates, how many are (currently) approved. This intentionally mirrors Housecall Pro's native reporting, including its known quirk: an estimate given last month but approved this month won't count as approved in either month's "Estimates approved" tile, because both tiles are scoped by *creation* date.
- **Approved this period** — the fix for that quirk. Counts estimates approved *within* the selected period regardless of when they were originally given, so an estimate created last month and approved this month correctly shows up this month.

**Estimator cards.** Any technician tagged `Estimator` (office staff who write estimates rather than do field work — `isEstimator`/`renderEstimatorCard` in `app.js`) gets an entirely different card instead of the standard one: the usual field-tech tiles (Jobs, Revenue, Leads, RCC sold, IFO, Accessory sold, ...) would all read zero for them, since those all derive from jobs they're never assigned to. Their card shows five tiles instead — Estimates given (creation-date scoped, as above), **Estimates approved**, **Approved this period**, **Closing %**, and **Revenue accepted**.

Unlike the regular scorecard, where Estimates approved and Approved this period are two genuinely separate, non-deduplicated tiles, an estimator's **Estimates approved** is a single de-duplicated number covering both at once (`computeEstimatorStats`/`unionById` in `app.js`): estimates given this period that are currently approved, plus estimates (given whenever) whose approval landed in this period — de-duplicated by id, so an estimate given *and* approved in the same period is never counted twice. That's the headline, ambiguity-free number Closing % (this combined approved count ÷ Estimates given) and Revenue accepted (sum of `approved_amount`, see below, across that same combined set) are both derived from — an estimate given last period but approved this one still lifts all three, crediting the estimator for closing older proposals rather than only ever measuring what they gave in the exact selected period; Closing % can exceed 100% in a period where more old proposals close than new ones are given. **Approved this period** sits alongside it as additional context, matching the field-tech card's tile of the same name and same underlying list (`techApprovedThisPeriodEstimates`) — it can be a subset of the headline "Estimates approved" number (e.g. an estimate given last period but approved this one shows in both), which is expected, not a discrepancy, since "Estimates approved" already absorbed it via the union above. The expandable detail list shows the same combined set behind "Estimates approved" (date given, date approved if applicable, customer, and amount if approved), so every estimate contributing to a tile above is visible in the list below it. Each item's displayed "Given [date]" (`renderEstimateItem` in `app.js`) uses `estimateGivenDate` — the same date field that decided whether that estimate counts as "given" for this tech — rather than always `created_at`, so Andy's list reads consistently with his tiles instead of showing a creation date that wasn't what actually attributed the estimate to that period. The list is sorted by that same date too, for the same reason.

`toPublicEstimate` (`scripts/sync.js`) also carries `estimate_number`, `customer_label` (first name + last initial, same minimal-PII convention as jobs), and `approved_amount` (cents — sum of the approved option(s)' `total_amount`, Housecall Pro's same cents-based money convention as jobs) to support this.

**How `approved_at` is actually determined.** Housecall Pro's API has no dedicated "approved at" field. The obvious stand-in — the approved option's own `updated_at` — turned out to be unreliable in practice: it bumps on *any* change to that option, including the resulting job's status progressing (scheduled → started → completed) long after the real approval decision, so an estimate approved in March could show an "approval date" from July just because its job wasn't finished until then. (A Housecall Pro webhook, `estimate.option.approval_status_changed`, does fire with an accurate timestamp the moment approval status actually changes — but consuming it would mean standing up a persistent server endpoint to receive it, a real piece of new infrastructure this otherwise fully static-site-plus-scheduled-polling project doesn't have. That remains the real fix if it's ever worth building.)

Instead, `sync.js` derives `approved_at` itself by diffing against the *previous* sync's `docs/data/estimates.json` (read back in via `loadPreviousEstimatesById` before that file gets overwritten): the first time a sync observes an estimate's `approved` flag flip from `false` to `true`, it stamps that estimate with *that sync run's own timestamp* — accurate to within one sync interval, which beats a field that can silently drift by months. An estimate that was *already* approved as of the previous sync just carries forward whatever `approved_at` that sync recorded.

The unavoidable gap: for an estimate that was already approved before this diffing approach shipped (or that first entered the sync window already approved), there's no prior observation to diff against, so `approved_at` is `null` — it drops out of every approval-date-scoped stat (Approved this period, Closing %, Revenue accepted on estimator cards) until Housecall Pro's approval status genuinely changes again. There's no way to retroactively recover a timestamp that was never observed.

"Approved" means an estimate has at least one option with `approval_status` of `approved` or `pro approved` (a pro manually marking it approved, e.g. after a phone call, counts the same as a customer clicking approve themselves).

**There's no `approved_at` field on an estimate.** The closest available signal is the approved option's own `updated_at`, used in `toPublicEstimate` (`scripts/sync.js`) as a best-effort proxy for when it was approved. This is usually accurate — `updated_at` bumps when the approval status changes — but could in principle be thrown off if an estimate is edited for an unrelated reason after approval, since that would also bump `updated_at` without a new approval happening. There's no better field available via the public API to avoid this.

**Estimates can't be fetched in date-chunks like jobs**, since the `/estimates` endpoint's only date filter is `scheduled_start`/`scheduled_end` (the on-site visit time — many estimates never have one). `fetchEstimatesInWindow` in `scripts/sync.js` instead fetches each `work_status` bucket (`unscheduled`, `scheduled`, `in_progress`, `completed`, `canceled`) separately, sorted newest-first, stopping each as soon as an estimate's `created_at` falls before the sync window — a partial mitigation against the same pagination drift that once silently dropped job records (see "Adjusting the data window" below), since no better one is available here.

## Adjusting the data window

`scripts/sync.js` fetches jobs from *at least* 62 days back through 13 days forward (`MIN_WINDOW_DAYS_BACK` / `WINDOW_DAYS_FORWARD`), plus however far back Jan 1 of the current year is — whichever is larger. The 62-day floor is so "This month" and "Last month" are always fully covered no matter what day of the current month it is (worst case: the last day of a 31-day month needs the full current month plus the full previous month behind it). The Jan-1 floor is what makes "Year to date" accurate; it's ~62 days in January and grows to ~365 by December, so the data file gradually grows over the year and resets smaller again each new January.

This doesn't bloat git history the way it might seem to — the sync commit is amended and force-pushed in place (see above), so the repo only ever carries one data commit's worth of history regardless of window size, just a bigger blob in that one commit as the year goes on.

**Going back further than the current year (e.g. multi-year trends or a rolling "Last quarter" that crosses years) isn't a small change.** That would mean either storing small periodic rollup summaries instead of full job detail for older data, or moving off git-committed JSON to a real database. Ask if you want that built out.
